# 要件定義: テーマ逆引き検索ツール

- サイト全体: 謎解き制作支援ツール集（Riddles）
- 本書の対象: 第1弾ツール「テーマ逆引き検索」
- ステータス: ドラフト（検討事項に未確定項目あり）
- 作成日: 2026-09-02

---

## 1. 背景・目的

謎解きでは、日本の中等教育までに学ぶ事柄のうち95%以上の人が暗記しているものが、テーマとして頻繁に出題される。教育内容に限らず、日常に関する「グループのもの」（例: 指の名前、曜日、干支、方角、トランプのマーク）も出題対象になり得る。

制作者が「答えにしたい単語」を先に決めた場合、その単語を構成できるテーマを探す作業は経験と時間を要する。本ツールは、答えの単語を入力すると、**その単語を「グループ内の要素から1文字ずつ拾う」ことで構成できるテーマを辞書から逆引き検索**し、拾い方まで提示することで、この作業を支援する。

### 例

入力「ひかり」→ 結果「指の名前」

| 答えの文字 | 拾い元の要素 | 要素内の位置 |
|---|---|---|
| ひ | ひとさし | 1文字目 |
| か | なか | 2文字目 |
| り | くすり | 3文字目 |

## 2. 用語定義

| 用語 | 意味 |
|---|---|
| グループ（テーマ） | 「指の名前」のような集合の名前 |
| 要素 | グループに属する個々の語。**ひらがなのよみ、または半角英字のみ**で登録する（おや / ひとさし / なか / くすり / こ）。漢字などの表記は持たない |
| 拾い | ある要素の中の1文字を、答えの1文字として採用すること |
| 正規化 | 濁点・半濁点・小書き文字などの表記ゆれを同一視するための変換 |

## 3. 機能要件

### 3.1 テーマ逆引き検索（利用者向け）

#### 入力

- 答えの単語（テキストボックス、1入力欄）
  - 受け付ける文字種: ひらがな・カタカナ・半角英字（カタカナはひらがなに、英大文字は小文字に統一して扱う）
  - 文字数上限: 10文字程度を想定（要検討 → §7-4）
  - 漢字・数字・記号が入力された場合はバリデーションエラーを表示する（かな変換対応は将来検討 → §7-4）

#### 検索オプション

| オプション | UI | 初期値 | 内容 |
|---|---|---|---|
| 許容する未マッチ文字数 | ドロップダウン（0〜3） | 0 | 答えのうち、拾えない文字を何文字まで許容するか。例: 1に設定すると「ひか」まで拾えて「り」が拾えないテーマも結果に含まれる |
| 表記ゆれを区別しない | トグル | ON（区別しない） | 濁点・半濁点・小書き文字（拗音・促音）を同一視して照合する |
| 同一要素からの複数拾いを許可 | トグル | OFF（不許可） | ONにすると、1つの要素から答えの2文字以上を拾うことを許す |

正規化（トグルON時）の内容:

- 濁点を除去して同一視: が→か、じ→し など
- 半濁点を除去して同一視: ぱ→は など
- 小書き文字を並字に同一視: ゃ→や、ょ→よ、っ→つ、ぁ→あ など
- カタカナ→ひらがな、英大文字→小文字の変換は、トグルに関わらず常に行う
- 長音「ー」は通常の1文字として扱う（直前の母音との同一視などの特別扱いはしない）。「ん」「ゐ」「ゑ」も同様に通常の1文字として扱う

#### マッチング判定

1. 入力文字列と辞書の全要素を正規化する（トグルONの場合）
2. 各グループについて、「答えの各文字」と「その文字を含む要素」の対応付けを求める
3. 制約:
   - 「同一要素からの複数拾いを許可」がOFF（初期値）の場合、**1つの要素から拾えるのは1文字まで**。答えに同じ文字が複数回現れる場合も、それぞれ別の要素から拾う必要がある
   - 同オプションがONの場合、1つの要素から複数の文字を拾ってよい（答えの各文字が「その文字を含む要素がグループ内に存在する」だけで拾える）
   - 答えの文字と要素の対応は順不同（答えの文字順とグループ内の要素順の一致は求めない）
4. 対応付けが「答えの文字数 −（許容する未マッチ文字数）」以上成立するグループを検索結果とする
   - オプションOFF時の判定は二部グラフの最大マッチング問題として実装する（実装メモ → §8）

#### 出力

- 条件を満たす**すべてのグループ**を表示する（複数候補があれば複数表示）
- 各候補について表示する内容:
  - グループ名、カテゴリ
  - 答えの各文字ごとの拾い元（要素名・要素内の何文字目か）。要素の表示は正規化前の登録内容で行い、拾った文字をハイライトする
  - 拾えなかった文字がある場合は、その文字を明示する（例: 「り」は拾えません）
  - 同一グループ内に拾い方が複数通りある場合の扱いは要検討（→ §7-2）
- 並び順: 未マッチ文字数の昇順（完全一致が先頭）→ 同数ならグループ名の五十音順
- 0件の場合はその旨と、オプション緩和（許容文字数を増やす）の案内を表示する

### 3.2 辞書管理（管理者向け）

大量のグループ・要素を継続的に登録していくため、登録作業の効率を最優先した管理画面を用意する。

#### 提供形態・アクセス制御

- 管理画面は**ローカル環境でのみ起動**する（例: `npm run admin`）。公開サイトの静的ビルドには一切含めない
- ローカル起動のみのため、ログイン等の認証機構は設けない
- 管理画面での編集は、リポジトリ内の辞書マスターファイル（JSON）への書き込みとして保存される。公開への反映は commit & push → 静的ビルドで行う（→ §5）

#### グループ一覧

- 全グループを一覧表示（グループ名・要素数・カテゴリ・公開状態・更新日時）
- グループ名・要素による絞り込み検索、カテゴリでのフィルタ

#### グループ登録・編集

- 入力項目:
  - グループ名（必須。例: 指の名前。こちらは漢字を含む自由な表記でよい）
  - カテゴリ（例: 教育 / 日常 / その他。マスタ管理は要検討）
  - 要素のリスト（必須。各要素は**ひらがなのみ、または半角英字のみ**で登録する。それ以外の文字種はバリデーションエラー。例: 曜日なら「にち, げつ, か, すい, もく, きん, ど」）
  - 備考（自由記述。出典や認知度に関するメモなど）
  - 公開 / 非公開フラグ（非公開のグループは検索対象から除外）
- 要素は**並び順を保持**する（「おや→ひとさし→なか→くすり→こ」の本来の順序に意味があるため）。並べ替え操作（ドラッグ&ドロップ等）を提供する
- 同名グループの登録時は警告を表示する（登録自体は可能とするかは要検討）

#### 一括インポート

- テキスト貼り付けによる複数グループの一括登録に対応する
- フォーマット案（1行1グループ）:

  ```
  指の名前: おや, ひとさし, なか, くすり, こ
  曜日: にち, げつ, か, すい, もく, きん, ど
  ```

  - `グループ名: 要素, 要素, ...`
  - 要素はひらがなのみ、または半角英字のみ（グループ編集画面と同じバリデーション）
- インポート前にパース結果のプレビューを表示し、確認後に登録する
- パースエラー（不正な文字種を含む要素など）・重複グループは行単位で報告し、正常な行のみ取り込めるようにする

#### 削除

- グループ単位・要素単位で削除可能
- 削除前に確認ダイアログを表示する

## 4. データ要件

辞書マスターはリポジトリ内のJSONファイルとして保持する（→ §5）。以下は論理モデル。

### Group（グループ）

| 項目 | 型 | 備考 |
|---|---|---|
| id | ID | |
| name | 文字列 | グループ名（例: 指の名前） |
| category | 文字列 | 教育 / 日常 など |
| note | 文字列 | 備考 |
| isPublished | 真偽値 | 非公開は検索対象外 |
| createdAt / updatedAt | 日時 | |

### Element(要素)

| 項目 | 型 | 備考 |
|---|---|---|
| id | ID | |
| groupId | ID | 所属グループ |
| order | 整数 | グループ内の並び順 |
| name | 文字列 | ひらがなのみ、または半角英字（小文字）のみ（例: か、ひとさし、do） |

- 検索高速化のため、正規化済みの文字列（normalizedName）を保存時に生成して持たせる（表記ゆれトグルOFF用に name も保持）

## 5. 非機能要件・アーキテクチャ

### 構成方針（決定済み）

**ローカル管理画面 + 静的ホスティング完結**の構成とする。サーバー・DBの常時運用は行わない。

```
[ローカル環境]                          [静的ホスティング]
管理画面（ローカル起動）                 GitHub Pages / Cloudflare Pages 等
  │ 編集・一括インポート                   │
  ▼                                      │ 検索ページ + 辞書JSONを配信
辞書マスター（リポジトリ内JSON）          ▼
  │ commit & push → 静的ビルド ──────▶ ブラウザ内で検索を完結
```

- 辞書のマスターデータはリポジトリ内のJSONファイルで管理する（変更履歴がgitに残り、revert可能）
- 検索はブラウザが辞書JSONを読み込んでクライアント側で完結する（検索時の通信なし）
- 管理画面はローカル専用（→ §3.2）。オンラインからの辞書編集は将来課題とする

### 非機能要件

- 辞書規模: 数百グループ・数千要素を想定（辞書JSONは数百KB程度に収まる見込み）
- 検索応答: 辞書読み込み後はブラウザ内計算のみで、体感即時（オプション変更時も即再検索）
- 対応環境: モダンブラウザ（PC / スマートフォン、レスポンシブ対応）
- サイト構成: 本サイトは複数の制作支援ツールを載せるハブ型サイト。共通ヘッダ・ナビゲーションからツールを選択できる構成とし、本ツールはその1つとして実装する
- ホスティング費用: 静的ホスティングの無料枠で完結すること

## 7. 検討事項（未確定・要相談）

1. **カテゴリのマスタ管理**: カテゴリを固定リストにするか、自由入力にするか
2. **同一グループ内の複数の拾い方**: 例えば「か」が「なか」にも「あかつき」にも含まれる場合、全パターン表示か代表1件か
3. **入力仕様の詳細**: 答えの文字数上限、漢字入力のかな変換対応の要否
4. **フレームワーク選定**: 構成（静的完結）は決定済み。公開サイトのビルドとローカル管理画面を1コードベースでどう組むか（例: Next.js静的エクスポート / Vite+React + ローカル管理サーバー）は実装計画時に確定する
5. **認知度メタデータ**: 「95%以上が暗記している」基準の管理方法（カテゴリと備考で足りるか、認知度レベルの項目を設けるか）

### 決定済み事項（2026-09-02）

- 同一要素からの複数拾い: オプションで切り替え可能とし、初期値はOFF（不許可）
- 答えの文字順とグループ内の要素順の対応: 制約に入れない（順不同のみ）
- 長音「ー」: 直前の母音との同一視はせず、通常の1文字として扱う
- 要素の登録形式: 「表記(よみ)」の分離はせず、ひらがなのよみのみ、または半角英字のみを登録する
- アーキテクチャ: **ローカル管理画面 + 静的ホスティング完結**。辞書マスターはリポジトリ内JSON、検索はブラウザ内で完結、管理画面はローカル起動のみ（認証不要）

## 8. 実装メモ（参考）

- 「同一要素からの複数拾い」OFF時のマッチング判定は「答えの文字（左）× グループの要素（右）」の二部グラフを作り、文字が要素に含まれるなら辺を張って最大マッチングを求める。マッチングサイズ ≥ 文字数 − 許容数 で採用。答え10文字・要素数十件程度なら Hopcroft–Karp どころか単純な増加路探索で十分高速
- 同オプションON時はマッチング不要で、答えの各文字について「その文字を含む要素が存在するか」を独立に数えるだけでよい
- 全グループ走査でも数百グループ規模なら性能問題はないが、事前に「正規化済み文字 → その文字を含む要素を持つグループ集合」の転置インデックスを作ると候補を絞り込める
